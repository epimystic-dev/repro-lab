# Research radar - 2026-10-25

Weekly digest of frontier signal on research-reproducibility and
evaluation-integrity defects, plus a note on what repro-lab built this
week and why.

## What the frontier is showing (last ~7 days)

1. **lm-evaluation-harness v0.4.13 release notes (EleutherAI)**: a
   batch of fixes for defects that silently corrupted published
   numbers - the few-shot sampler could draw the document under test
   into its own demonstrations; a scalar seed read from a config file
   was not normalized to the tuple form the harness expected;
   `gen_prefix` was resolved against the wrong document; and
   `enable_thinking=True` was now disallowed on multiple-choice /
   loglikelihood tasks after previously failing silently. *Why this
   matters*: these fingerprints survive into the written
   `results.json`, so a shape-level linter can see them without
   rerunning anything. Source: github.com/EleutherAI/lm-evaluation-harness/releases.
2. **LightEval sampling-param silent-drop (huggingface/lighteval
   tracker)**: `top_k`, `min_p`, and `presence_penalty` are accepted
   by the config model but then not sent to the backend; nothing in
   the resulting file warns that the run used different sampling than
   requested. *Why this matters*: a linter that compares declared
   sampling against the sampling actually recorded on
   per-request entries catches this with no network and no replay.
   Source: github.com/huggingface/lighteval/issues.
3. **PromptLayer 2026 "Why LLM Evaluation Results Aren't
   Reproducible"**: converges with the harness release notes on a
   seven-item comparability checklist (model pin, seed pin, limit
   off, consistent few-shot, bootstrap-consistent CIs, declared tasks
   all reported, harness git-hash). *Why this matters*: the checklist
   is largely shape-level and auditable offline. Source:
   promptlayer.com/blog/why-llm-evaluation-results-arent-reproducible.
4. **arXiv 2607.17242 - AI Bill of Materials Completeness in Hugging
   Face Models (large-scale study of 97,940 models)**: auto-generated
   AIBOM fills every required structural field but averages ~19.51%
   model-card completeness; intended-use, ethical-considerations and
   energy fields are almost never filled. *Why this matters*: a
   card-completeness linter against the published HF field list has a
   measurable floor to raise. (Noted; deferred this week - needs YAML
   parsing, out of stdlib scope.)
5. **arXiv 2510.18013 - JunoBench crash-root-cause dataset**: 74.3% of
   Kaggle notebook-specific crashes stem from cells being executed in
   an incorrect sequence. *Why this matters*: the fingerprint
   (execution_count ordering, cell source vs recorded outputs) is in
   the `.ipynb` file; an offline linter can expose it before the
   notebook is published.
6. **arXiv 2605.01560 - FlowBook: Enforcing Reproducibility in
   Computational Notebooks**: formalizes the out-of-order execution
   defect class and demonstrates it against 61 Kaggle notebooks.
   *Why this matters*: the paper is a public source for the exact
   defect taxonomy a notebook linter needs.
7. **arXiv 2603.22726 - A Study of Scientific Computational Notebook
   Quality**: only ~24% of GitHub notebooks are fully executable
   top-to-bottom, and ~11% reproducible after manual troubleshooting.
   *Why this matters*: the pre-publish catch-rate ceiling is high;
   there is real room for a lint-at-commit-time tool.
8. **arXiv 2610.00421 - Scores That Hold, Benchmarks That Leak**:
   dataset contamination in public brain-tumor MRI classification.
   *Why this matters*: another instance of the contamination/leakage
   class the lab's `splitcheck` candidate targets. (Noted; deferred -
   near-duplicate detection without a dependency is unreliable.)
9. **arXiv 2607.12278 - Auditing Data Leakage in Whole-Slide Image
   Multimodal Benchmarks**: documents patient-level and
   institutional-level leakage patterns. *Why this matters*: real
   examples feed the eventual splitcheck rule set; deferred for now.
10. **Pip supply-chain / unpinned-requirements guides (multiple 2026
    writeups + Hacker News + GitHub security issue tracker)**:
    continuing drumbeat that loose version pins are a reproducibility
    AND supply-chain hazard. *Why this matters*: supports the lab's
    `pinaudit` candidate; deferred this week in favor of two tools
    that are a better charter fit.

## What we chose to build and why

Two artifacts cleared the bar this run; both are standard-library
only, offline, clean-room, and address signals from the last few
days with distinct audiences:

- **`evalrunlint`** - the lab's charter candidate #1
  (`evalrunlint - comparability linter for evaluation-harness result
  files`). Directly addresses signals (1), (2) and (3) above with
  fifteen offline rules against the file every harness writes. For
  reviewers and anyone wiring reproducibility checks into pre-commit
  or CI around a `results.json` artifact.
- **`nbexport`** - the lab's charter candidate #6
  (`nbexport - notebook to script in recorded execution order, with
  an order report`). Addresses signals (5), (6) and (7) with nine
  offline rules against the `.ipynb` file plus a script exporter in
  two modes (linear and executed). For reviewers of published
  notebooks and authors sharing them.

Rejected this week:

- **`cardcheck`** (candidate #3) - the signal is real (study at 97,940
  models, 19.51% completeness), but complete HF field-list parsing is
  cleaner with a YAML dependency, and the lab's standard-library-only
  rule costs the clarity. Deferred.
- **`splitcheck`** (candidate #2) - near-duplicate detection without a
  dep is unreliable; a shape-only id-overlap check is a weak version
  of the real tool. Deferred until the problem can be addressed to a
  world-class bar within the lab's constraints.
- **`pinaudit`** (candidate #4) - overlaps `epimystic-lab`'s
  general-purpose file-hygiene territory more than the lab's charter.
  Will revisit framing before building.

## Honest scope

A clean run from either tool means the record is internally
consistent and complete against the named checklist. Neither tool
re-runs the experiment or asks whether the reported numbers are
correct. Each tool's README has its own false-positive section.
